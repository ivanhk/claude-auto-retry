## 修复方案：菜单路径自动 continue + tmux 状态栏显示下次 continue 时刻

### 三个问题（均由日志 + 代码确认）

**问题 1 — 菜单路径等待到点不发 continue（核心，用户抱怨的"没自动 continue"）**
日志：菜单 `00:20 PDT` 设 `Waiting 18060s`（→ 05:21），但 reset 实际 `1:30am`。reset 后 banner 消失，monitor 仍在傻等到 05:21；到点后 `monitor.js:229` 的 Gate B `!isRateLimited(...) → 'user-continued'` **不发 retryMessage**。
根因：`waiting` 分支的 Gate B 假设"banner 消失=用户手动继续"，对 monitoring 路径成立，对**菜单路径不成立**——菜单路径是 monitor 自己选了 "Stop and wait"，从没注入过 continue，banner 消失只意味着 limit 解除，必须主动发 continue。

**问题 2 — 菜单路径 reset 时间解析（5h fallback）**
`monitor.js:187` 从菜单 capture 找 reset，但菜单盖住 banner/hud 行时 `findRateLimitMessage` 返回 null → 已有的 `resetWaitFromCache` 依赖"菜单前先缓存"，但 limit 首次出现就弹菜单，monitoring 没机会缓存。
修法：菜单按 Enter 后，**短暂等待 + 重新 capture**（菜单关闭、banner/hud 重渲染），从新 capture 解析 reset。这是 `processOneTick` 内的局部改动。

**问题 3 — tmux 状态栏没显示**
`bin/tmux-status.sh` 的 `waiting)` 分支只显示剩余倒计时（`⏳AR 3h32m`），且用户 `.tmux.conf` 根本没配置 status-right。状态文件**已在写**（`waitUntil` epoch 秒在位）。

---

### 改动 1：`src/monitor.js` — 菜单路径标记来源 + 到点必发 continue

**(a) state 增加来源标记**
`createMonitorState` 加 `_waitingViaMenu: false`。
- 菜单路径（`monitor.js:206` 设 `status='waiting'` 处）置 `state._waitingViaMenu = true`。
- `enterUsageWait`（`monitor.js:101`）置 `state._waitingViaMenu = false`。
- 回到 monitoring 时（`monitor.js:230`、其它 reset attempts 处）置回 false。

**(b) Gate B 区分两条路径**（`monitor.js:229-232`）
```js
// 菜单路径是 monitor 自己选了 "Stop and wait"，banner 消失只代表 limit 解除——
// 从未注入过 continue，必须主动发；monitoring 路径 banner 消失通常意味着用户手动继续，不发。
if (!isRateLimited(stripped, config.customPatterns, RATE_LIMIT_TAIL_LINES) || resumedAfterLimit(...)) {
  if (state._waitingViaMenu) {
    // 落到下面的 retry 发送逻辑，而不是 return 'user-continued'
  } else {
    state.status = 'monitoring'; state.attempts = 0; state._waitingViaMenu = false;
    return 'user-continued';
  }
}
```
具体实现：把菜单路径下"banner 消失"的情况，**不 return**，而是 fall through 到已有的 retry 发送段（`monitor.js:261-266`：`attempts++/sendKeys/retried`），并清 `_waitingViaMenu`。用条件跳过 `'user-continued'` return 即可，改动局部。

**(c) Gate A 也放行菜单路径的 banner 消失**（`monitor.js:220`）
现在 Gate A `Date.now() < waitUntil && !resumedAfterLimit → return 'waiting'`：菜单路径下 reset 早过、banner 已消失但仍被 park 到 waitUntil。改成：菜单路径下若 `!isRateLimited`（banner 没了）也放行 fall through（不死等）。即：
```js
const limitGone = !isRateLimited(stripped, config.customPatterns, RATE_LIMIT_TAIL_LINES);
if (Date.now() < state.waitUntil && !resumedAfterLimit(...) && !(state._waitingViaMenu && limitGone)) return 'waiting';
```
这样菜单路径一旦发现 limit 解除（即便没到 waitUntil）就立即 continue，不再傻等。

### 改动 2：`src/monitor.js` — 菜单确认后重新 capture 解析 reset（修 5h fallback）

菜单块按 Enter 后（`monitor.js:184` 之后），加一次"延迟重新 capture"：
```js
await tmuxAdapter.sendKey(pane, 'Enter');
// 菜单关闭后 banner/statusLine 重渲染；短暂等待再 capture，从新画面解析 reset，
// 避免 5h fallback（菜单 capture 里 banner 被盖住）。
let parsed = null; let message = null;
for (const delay of [250, 500, 1000]) {
  await new Promise(r => setTimeout(r, delay));
  const reRaw = await tmuxAdapter.capturePane(pane, 120);
  const reStripped = stripAnsi(reRaw);
  message = findRateLimitMessage(reStripped, config.customPatterns);
  parsed = message ? parseResetTime(message) : null;
  if (parsed) break;
}
// 仍解析失败才走 resetWaitFromCache → fallback（保留现有兜底）
```
保留原有 `findRateLimitMessage(stripped)`（菜单 capture）作为第一尝试，重新 capture 作为第二尝试。解析成功才缓存 `lastResetWaitMs`（现有逻辑）。

### 改动 3：`bin/tmux-status.sh` — waiting 分支显示下次 continue 时刻

`waiting)` 分支（第 61-69 行）改为显示绝对时刻：
```sh
waiting)
  waitUntil=$(... '"waitUntil":[0-9]*' ...)
  # 下次 continue 时刻（本地时间 HH:MM）。BSD/GNU date 都支持 -r。
  printf '⏳AR %s' "$(date -r "$waitUntil" +%H:%M 2>/dev/null || date -d @"$waitUntil" +%H:%M 2>/dev/null)"
  ;;
```
`date -r` 兼容 macOS/BSD；`date -d @` 兼容 GNU（Linux）。优先 `-r`，失败回退 `-d @`。

### 改动 4：`~/.tmux.conf` — 配置 status-right（用户的私人配置，单独说明）

当前 `.tmux.conf` 只有一行 `default-shell`。需加（**不在本次代码改动里，作为给用户的说明**）：
```tmux
set -g status-interval 5
set -g status-right "#(/usr/local/bin/claude-auto-retry-tmux-status '#{pane_id}' '#{socket_path}') | %H:%M"
```
注意：用 `claude-auto-retry-tmux-status` 的**绝对路径**（tmux server 环境可能没 nvm PATH）。该 bin 已在 package.json `bin` 里注册，brew node 下装在 `/usr/local/bin/`。
